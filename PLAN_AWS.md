# PLAN_AWS.md — tmct.polycode.co.uk: AWS accounts, edge, and CI lift-and-shift

Plan to move tmct's public site from GitLab Pages to a new AWS-hosted main site at
**`tmct.polycode.co.uk`**, mirroring seonix's account/edge/CI pattern (`seonix/AWS_ACCOUNTS.md`,
`seonix/infra/`, `seonix/docs/AWS_SETUP.md`). Written 2026-07-26 against tmct 3.0.6 and the
`.gitlab-ci.yml` of the same date. Phases 1–8 are live — see `AWS_ACCOUNTS.md`'s "Provisioning status (2026-07-26)" for current state.

**Lift and shift, no content changes.** The artifact stays exactly what `npm run build:ask-bundle`
+ `npm run demo:build` produce into `public/` today — same pages, same bundles, same
service worker, same precompressed siblings. Only the host, the pipeline's deploy job, and the
URL references change. The npm package, the GitLab repo, and `publish:npm` are untouched except
for the `homepage` field.

## What is being moved (current surface, with references)

- **The `pages` job** (`.gitlab-ci.yml:487-514`): main-only, consumer-paths-gated, runs
  `npm ci` → `npm run build:ask-bundle` → `npm run demo:build`, then publishes `public/` as a
  GitLab Pages artifact. This is the job the new AWS deploy job replaces.
- **The built site**: ~85 MB, 10 HTML pages, generated by `scripts/build-demo-site.mjs` into
  `public/` (mostly gitignored — only `index.html`, three tracked `.mjs` files, `engine-shims/`
  and `screenshots/` are in git; see `.gitignore:73-105`). The build writes precompressed
  `.br`/`.gz` siblings (28 pairs) for every HTML file and every `.js/.mjs/.json` ≥ 50 KB
  (`build-demo-site.mjs:490-542`), and a service worker `public/tmct-sw.js` with cache name
  `tmct-precache-v<version>` (`build-demo-site.mjs:474-479`).
- **The post-deploy smoke** (`scripts/post-deploy-smoke.mjs`, run by `smoke:post-deploy` at
  `.gitlab-ci.yml:525-537`): polls the URL taken from `package.json`'s `homepage` field, checks
  the npm `latest` version against the deployed site's `version.txt`, and — hard requirement on
  any new host — that `vendor/wink.js` comes back with a `content-encoding` response header
  (`post-deploy-smoke.mjs:54-64`). Changing `homepage` repoints the whole smoke; there is no
  separate URL config.
- **The live URLs**: `https://polycode-projects.gitlab.io/the-mechanical-code-talker/`
  (canonical, in `package.json:28`) 308-redirects to the GitLab unique domain
  `https://the-mechanical-code-talker-36445d.gitlab.io/`, which serves the site. Both appear in
  docs (full list in the reference-update section below).
- **E2E tests**: 52 files under `test-e2e/`, node's built-in test runner (`test:e2e`,
  `package.json:92`), 27 of them driving Chromium via the `playwright` library. Every browser
  test serves a locally built site snapshot through
  `test-e2e/helpers/static-server.mjs` / `test-e2e/helpers/demo-site.mjs` — none targets a
  deployed URL today. The only deployed-URL check in the repo is the smoke above. The
  e2e-against-AWS requirement is new plumbing, specified below.

## Phase 4 — infra port (CDK)

Copy `seonix/infra/` (`cdk.json`, `package.json` as a root npm workspace, `tsconfig.json`,
`bin/app.ts`, `lib/apex-stack.ts`, `lib/website-stack.ts`) with the Phase-2 renames, context
default `hostname=tmct.polycode.co.uk`. The apex stack ports unchanged. The website stack keeps
its shape — imported us-east-1 cert by ARN, OAC S3 origin, `PRICE_CLASS_100`,
`REDIRECT_TO_HTTPS`, conditional Route53 A-record, RETAIN-for-prod bucket policy — with three
deliberate differences:

1. **Deployment source is `../public`, not `../site`** — and unlike seonix (which deploys a
   checked-in `site/`), tmct's site is generated, so the CI job builds it fresh before
   `cdk deploy` (Phase 5). Nothing generated gets committed; `public/`'s gitignore status is
   unchanged.
2. **Compressed serving must survive the move.** GitLab Pages serves the build's `.br`/`.gz`
   siblings; `post-deploy-smoke.mjs` fails the pipeline if compression disappears, and
   `reports/PAGE_WEIGHTS.md`'s numbers depend on it. Split handling:
   - Everything ≤ 10 MB (including `vendor/wink.js`, 3.7 MB): CloudFront's own on-the-fly
     compression (`compress: true`, already in the seonix template) serves gzip/brotli. The
     smoke's `vendorEncoding()` check passes with no extra work.
   - Assets over CloudFront's 10 MB compression ceiling — today exactly one,
     `chat-seed.json` (40.5 MB raw, 2.1 MB brotli): serve the build's precompressed siblings.
     Upload siblings with real metadata (scoped `BucketDeployment`s or scoped sync passes:
     `*.br` with `Content-Encoding: br`, `*.gz` with `Content-Encoding: gzip`), and replace the
     template's SPA-rewrite CloudFront Function (dead weight for tmct — every tmct URL has a
     file extension) with a viewer-request function that rewrites the named oversized paths to
     their `.br`/`.gz` sibling by `Accept-Encoding`. Bake the path list in at deploy time from
     the build output rather than guessing in the function; `CACHING_OPTIMIZED` already
     normalizes `Accept-Encoding` into the cache key, so no custom cache policy is needed.
3. **`BucketDeployment` sizing**: the 85 MB payload needs the deployment Lambda's memory (and if
   needed ephemeral storage) raised above CDK defaults. If asset churn or Lambda limits become
   annoying, the fallback is publishing content from the CI job via the three-pass
   `aws s3 sync` (the `fast-deploy-web.sh` mechanism, plus the two metadata passes) and leaving
   CDK to own only the infra — a deviation from the seonix template, so take it only if the
   default hurts.

`scripts/fast-deploy-web.sh` ports with `SITE_DIR` defaulting to `public`.

## Phase 5 — DNS and certificate

Same operator runbook as `seonix/docs/AWS_SETUP.md` §7–8:

1. Deploy `tmct-prod-apex` (public hosted zone `tmct.polycode.co.uk` in tmct-prod).
2. Copy the stack's `Nameservers` output into an `NS` record for `tmct.polycode.co.uk.` in the
   parent `polycode.co.uk` zone in polycode-management (manual, TTL 300).
3. Request the ACM cert for `tmct.polycode.co.uk` via CLI in **us-east-1**, DNS-validated; the
   validation CNAME goes into the now-delegated child zone in tmct-prod. Record the ARN as
   `TMCT_PROD_CERT_ARN`. (CDK only ever imports this cert by ARN.)
4. Deploy `tmct-prod-prod-website` with hostname, certArn, hostedZoneId, zoneName in context —
   the stack writes the A-record itself.

**Deliverable**: `docs/AWS_SETUP.md` in this repo — the ported runbook, including the
"manual steps that cannot be scripted away" list (account creation, IDs into trust JSONs, SSO
assignments, the admin-role grant, NS delegation, ACM validation CNAME, CI variables, and the
npm publish that carries the homepage change).

## Phase 6 — CI pipeline swap

All in `.gitlab-ci.yml`; stages stay `test`, `e2e`, `deploy`, `verify`.

- **New `deploy:website` job** (deploy stage), modeled line-for-line on seonix's
  (`seonix/.gitlab-ci.yml:229-249`) but building the site first:
  - image `nikolaik/python-nodejs:python3.13-nodejs24` (node for the build, pip for awscli);
    `id_tokens: GITLAB_OIDC_TOKEN: aud: https://gitlab.com`.
  - rules: never on `schedule`; then `$CI_COMMIT_BRANCH == "main" && $PROD_AWS_DEPLOY_ROLE_ARN`
    with `changes: *consumer-paths` — the same trigger set as today's `pages` job, and the same
    fail-closed variable guard as seonix (job absent until CI variables exist).
  - script: `npm ci` → `npm run build:ask-bundle` → `npm run demo:build` (the exact `pages` job
    build steps, `.gitlab-ci.yml:499-511`) → `source scripts/assume-aws.sh prod` → `cd infra` →
    `npx cdk deploy tmct-prod-prod-website --require-approval never` with the context values
    from the CI variables. No artifact upload — the 85 MB stops transiting GitLab artifacts.
- **`pages` stays until cutover** (Phase 8), so both hosts publish in parallel during burn-in.
- **`smoke:post-deploy`**: `needs: [publish:npm, pages]` becomes
  `needs: [publish:npm, deploy:website]` at cutover. No other change — it follows
  `package.json`'s `homepage` automatically.
- **CI variables** (via `glab variable set`, prod ones masked + environment-scoped, mirroring
  `seonix/docs/AWS_SETUP.md` §10): `CI_AWS_ACTIONS_ROLE_ARN`, `CI_AWS_DEPLOY_ROLE_ARN`,
  `PROD_AWS_ACTIONS_ROLE_ARN`, `PROD_AWS_DEPLOY_ROLE_ARN`, `TMCT_PROD_ACCOUNT_ID`,
  `TMCT_PROD_CERT_ARN`, `TMCT_PROD_ZONE_ID`.
- The tmct-ci account and its any-branch trust policy are provisioned for branch-scoped review
  deploys, same as seonix's ci account. Note honestly: seonix has **no CI job implementing
  that** — the account and the `slug` plumbing exist, the job does not. Same posture here:
  provision the account now (cheap, symmetric), write the branch-deploy job only when a need
  appears. A branch deploy also needs its own hostname/cert story (the template's `hostname` is
  a single context value with no per-slug derivation) — design that then.

## Phase 7 — e2e against the AWS deployment

The requirement: pipeline e2e tests that run against the version actually deployed to AWS.

1. **Base-URL plumbing** in `test-e2e/helpers/`: when `TMCT_E2E_BASE_URL` is set, the site
   fixture returns `{ origin: process.env.TMCT_E2E_BASE_URL }` instead of building a local
   snapshot (`buildDemoSiteSnapshot`, `demo-site.mjs:25-40`) and binding a local server
   (`serveDirectory`, `static-server.mjs:37-73`). Unset, nothing changes — the existing local
   e2e jobs are untouched. One helper edit, no per-test changes for tests that already go
   through the fixture; the handful of browser tests that call `serveDirectory` directly get the
   same switch in one place if they share a helper, else individually.
2. **New `e2e:deployed` job** (verify stage): `needs: [deploy:website]`, main-only, never on
   schedule, chromium via the existing `.e2e-web-base` install pattern, runs the page-serving
   browser channels (the `pages-*` test files — start with the `e2e-web-index` set: `pages-home`,
   `pages-index`, `readme-examples`, and grow toward the full browser matrix once stable) with
   `TMCT_E2E_BASE_URL=https://tmct.polycode.co.uk`. `retry: 2` for edge-propagation flake,
   `allow_failure: true` for the burn-in period only — flip it to blocking once it has a green
   history, since a deployed-site check that can't fail the pipeline isn't doing its job.
   `e2e-tui` / `e2e-cli` stay local-only: they exercise the CLI/TUI, not the site.
3. All deployed-site tests are read-only page loads (navigation + DOM assertions), so running
   them against prod is safe. The 5-minute edge cache plus the deploy's `/*` invalidation is the
   same freshness model seonix's `behaviour:prod` runs under.
