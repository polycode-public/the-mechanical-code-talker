Drafted 2026-08-05 from the operator's claims notes (`claims-notes.txt`, kept untracked),

## Dispatch contract (applies to every task)

Each task is self-contained: it names its files, quotes the current state it expects, gives
the exact change, and ends with acceptance commands. An implementing agent needs no other part
of this doc and no repo-wide survey.

Rules for every dispatched agent, restated in every brief:

- **Stop rule.** If the tree does not match what the task quotes (a string is absent, a file
  is missing, a count differs), stop and report the mismatch. Do not improvise.
- **Tests.** `npm run test:smoke` after any edit, `npm run test:fast` plus the task's named
  blast-radius files before committing. Never the full suite, never e2e — those run once,
  coordinator-side, at the push.
- **Site pages.** `public/` demo pages are gitignored build outputs; run `npm run demo:build`
  before reading one. `public/index.html` and the `*-about.html` files are hand-authored and
  tracked.
- **Git.** Commit as `Antony at Polycode <antony@polycode.co.uk>`. Stage by explicit path,
  never `git add -A`. Never stash/reset/checkout-- /clean. Never push. Do not touch the
  untracked `publish-notes.txt` or `claims-notes.txt`.
- **Comments.** No comment may cite this plan, a date, an item number, or a conversation.
- **Prose.** All page copy and JSON-carried sentences follow
  `.claude/skills/plain-prose/SKILL.md`. Claims stated flat. No exclamation marks anywhere on
  the claims surface.
- **Honest-miss constitution.** No rig may weaken it: a refusal in a rig is data, never a
  failure to hide. Where a claim's number would tempt a fix that guesses instead of refusing,
  the claim is wrong, not the refusal.

## Open questions for the operator

Answer these before dispatch. Each names what blocks on it and a recommended answer.

1. **Placement: index section or a separate claims.html?** Blocks T14 (and the index edit
   inside it). Recommended: a separate `claims.html` in the site build with its own canonical
   URL, plus one short teaser card on the index linking to it. The index already carries the
   hero, the grid, and the narrative sections; the claims surface wants a stable URL to link
   from launch posts, and receipts.html set the precedent for a standalone evidence page.
2. **The labelled corpus for C2/L2.** Blocks T11. Recommended: author a committed 200-item
   set under `test-benchmarks/claims/ground-gate.jsonl` — 100 statements the shipped corpus
   can ground (drawn from tier2/wordnet content), 100 it cannot (well-formed but ungrounded,
   plus malformed shapes), each hand-labelled `groundable: true/false`. Authored in-repo, so
   no external licence. Size and the 50/50 split are the call to confirm.
3. **E1's QA set and extension corpus, licensing included.** Blocks T12. Recommended:
   OpenBookQA (Apache-2.0, verified) as the source of the committed 100-question sample;
   `wordnet-xl` as the loaded corpus between the two runs. CommonsenseQA is not
   recommended: its repo states no dataset licence. Also confirm the scoring rule: a
   multiple-choice item counts correct when the chat answer names the gold choice's term
   (exact/variant match), a refusal counts as unanswered, never as wrong-and-right shared
   credit.
4. **E2's frequency list and domain lexicon.** Blocks T13. Recommended: for OOV, a committed
   sample from a clearly-licensed frequency list (the wordfreq project's data is CC BY-SA
   4.0 — a 5,000-lemma top-slice fixture with attribution); SUBTLEX-US is research-only and
   not recommended for a commercial site. For the domain lexicon: a code-terms lexicon
   fixture (the code domain is already native via the index/graph path), with cooking as the
   fallback if you want a nontechnical demo domain.
5. **Wikidata SPARQL adapter: in or out of this pass?** Shapes T9. Recommended: out. Ship
   the adapter interface, the contract test, and the shipped Wikipedia adapter passing it;
   the notes themselves allow stubbing the second adapter. Wikidata lands as a follow-on
   with its own task when wanted.
6. **C7's domains and hardware.** Blocks T10. Confirm: (a) blocksworld and gripper are
   authored as committed English rule sets through the same teach path as Hanoi — there is
   no PDDL input to reuse; (b) the shipped Hanoi joins them as a third envelope column;
   (c) which machine's numbers are canonical for the published JSON (the rig names hardware
   in its output either way, and the in-page button prints the visitor's own number beside
   it).
7. **L3's equivalence rule.** Blocks T8. Recommended: two answers are equivalent when they
   have the same miss/non-miss status and cite the same fact ids; wording may differ.
   Byte-equality is C4's bar, not L3's.
8. **Threshold seeding.** Shapes T1. Each `claim:<name>` exits nonzero when the measured
   value regresses past a committed threshold. Recommended: the first committed run's value,
   with a stated per-claim margin (latency +20%, rates −2 points absolute), thresholds
   stored in each results JSON so the page can show them.
9. **The "benchmark this device" button (C7).** Confirm it ships in this pass. Recommended:
   yes — the plan engine already runs in the browser, and one mid-size instance solved
   client-side is the cheapest live proof on the page.

### T1 — the claims harness: schema, writer, thresholds, freshness guard (Sonnet)

Files: new `scripts/claims/lib.mjs`, new `scripts/claims/schema.json`, `package.json`, new
`test/estate/claims.test.mjs`, new `results/claims/README.md`.

1. `schema.json`: every `results/claims/<name>.json` carries `name`, `generatedAt`,
   `commit`, `hardware` (string, may be "ci"), `value` (number), `unit`, `threshold`
   (`{direction: "max"|"min", value: number}`), `sources` (array of repo paths), and for
   extensibilities `before`/`after`/`delta` in place of `value`. Extra per-claim fields
   allowed under `detail`.
2. `lib.mjs`: `writeClaim(name, payload)` validates against the schema, stamps
   `generatedAt`/`commit`, writes `results/claims/<name>.json`, and exits nonzero when the
   value regresses past the committed threshold (read the previous committed file for the
   threshold; a first run seeds it per the answer to Q8).
3. `package.json`: `"claims": "node scripts/claims/run-all.mjs"` plus one `claim:<name>`
   line per rig as later tasks add them; `run-all.mjs` runs every `claim:*` script and
   fails if any fails.
4. `test/estate/claims.test.mjs`: for every block the claims page declares (it reads the
   page's block manifest from `scripts/site-pages.mjs` once T14 lands; until then, every
   JSON present in `results/claims/`), assert the JSON parses, validates against the
   schema, and `sources` paths exist. Model it on `test/estate/receipts.test.mjs` — quote
   that file's structure before writing.

Acceptance: `npm run claims` exits 0 with zero rigs (vacuously); `node --test
test/estate/claims.test.mjs` passes; `npm run test:fast` passes.
